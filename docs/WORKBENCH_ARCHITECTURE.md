# 个人投资工作台架构草案

这份文档保留“规划”职责，但只记录仍然有决策价值的内容。

目标是三件事：

- 标清哪些已经完成
- 标清哪些还没完成
- 把最近发现、优先级更高的事项插入进去

更偏使用说明的内容放在 [README.md](/Users/lilinxing/Codes/quant/README.md:1)。

## 总目标

- 数据可信：MySQL 作为主数据源
- 工作流闭环：同步、查询、选股、修复、研究都在同一入口完成
- 模块清晰：页面、服务层、抓数层、研究层分工明确
- 可审计：关键任务进入任务表，方便回看和排查
- 可扩展：后续可继续接自选股、笔记、agent 能力

## 当前主链路

```text
Web / CLI
  -> service layer
  -> quant_data / MarketDataClient
  -> MySQL + data/cache
```

当前已经确认的基础判断：

- `MySQL` 是主数据源
- 历史本地日线 CSV 仓库已经移除
- `data/cache/` 继续作为第三方接口缓存层
- `sync_runs` / `sync_run_items` 是当前任务状态和审计入口

## 新增的高优先级事项

这是最近随着系统演进，我们发现优先级其实更高的事情。它们应插到原规划前面：

### P1. 同步/修复后自动刷新 `daily_bar_indicators`

原因：

- `daily_bar_indicators` 表还在
- 但当前主同步链路不会自动刷新它
- 这会让数据库指标表和实际日线数据脱节

### P1. 建立独立的股息率因子层

原因：

- 现在股息率主要是选股时临时取值或估算
- 还没有稳定的日级股息率表
- 这会限制后续策略、回测、解释和页面展示

### P1. 把修复/选股任务纳入统一后台任务体系

原因：

- 同步任务已经后台化
- 修复和选股还没有完全共享同一套任务抽象
- 任务体验和审计能力不一致

### P2. 行情页增强

原因：

- 当前 K 线可看，但研究深度不够
- 缺少更实用的指标和区间能力

建议内容：

- MA 展示
- 成交量展示
- 复权切换
- 区间切换

## 建议代码演进

这部分保留方向，但不作为强制重构任务。

当前主要代码边界：

```text
src/
  quant_backtest/
  quant_data/
  quant_web/
```

建议演进原则：

- 不为了目录好看而重构
- 新功能优先放进正确边界
- 页面层只做请求解析、响应组装和展示
- 服务层负责业务编排
- 抓数与质量逻辑优先放在 `quant_data/`
- 数据访问和研究逻辑继续从页面层剥离

长期如果规模继续增长，再考虑逐步拆成：

- `quant_market`
- `quant_strategy`
- `quant_tasks`
- `quant_agent`

但这不是当前优先级。

## 建议路线

按现在的真实优先级，建议这样排：

### 第一优先级

- 同步/修复后自动刷新 `daily_bar_indicators`
- 建独立股息率因子表
- 把修复和选股任务统一进后台任务体系

### 第二优先级

- 行情页增强：MA、成交量、复权、区间
- 单股最近同步状态
- 选股结果归档

### 第三优先级

- 自选股
- 股票笔记
- 策略配置化
- 多策略对比

### 第四优先级

- agent 工具协议
- agent 调用审计
- 基于工作台数据的研究任务流

## 暂时不建议优先做的事

- 为了目录漂亮做大规模重构
- 过早抽很多层抽象
- 把回测包装成“完整平台”但底层口径还没统一
- 让 agent 直接绕过服务层读写数据库

## 维护方式

以后更新这份文档，尽量只做三种动作：

1. 把已完成事项从“未完成”移到“已完成”
2. 把新发现的高优先级事项插入“新增的高优先级事项”
3. 删除已经没有决策价值的长描述
